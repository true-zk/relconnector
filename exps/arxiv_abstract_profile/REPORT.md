# Arxiv Abstract 分阶段性能实验

## 配置与样本

2026-10-16，本地 `rel-arxiv.sqlite` 的 `papers.Abstract`。在 `Paper_ID % 11 = 0` 的 20,252 条不同摘要中，按 GloVe tokenizer 的实际输出长度分桶；每个常见桶抽取 3 组、每组 128 条，共 1,152 条。单 CPU 线程、300 维 GloVe、原直接路径内部 batch 8；本地与共享缓存各 64 MiB，磁盘缓存关闭。共享缓存试验是单进程，未包含多进程锁竞争。详细逐批原始值在三个 JSON 文件中。

## 原实现的分阶段耗时

表中数字是 3 组 128 条摘要的**每组墙钟中位数**，单位毫秒。冷是首次出现，热是同一组再次转换。

| token 数 | 冷 TensorFrame | 热 TensorFrame | 冷分词 | 冷词向量查找 | 冷池化 | 热缓存查询（本地 / 共享） |
|---|---:|---:|---:|---:|---:|---:|
| 0–63 | 20.3 | 3.7 | 7.8 | 2.0 | 5.4 | 1.2 / 1.1 |
| 64–127 | 29.9 | 3.8 | 13.0 | 3.0 | 8.4 | 1.2 / 1.2 |
| 128–255 | 41.8 | 3.9 | 19.1 | 4.0 | 12.5 | 1.2 / 1.4 |

冷路径的分词与池化增长最明显：128–255 桶二者合计约 31.6 ms，占 41.8 ms 冷转换的约 76%。热路径基本与 token 长度无关；热缓存查询约 1–1.4 ms，但本次任务的关键路径是首次编码。`frame_prepare` 约 1–1.4 ms，`text_expand` 约 0.15 ms。共享缓存和本地缓存在本试验中的总延迟相近；这不能外推到多进程争锁情形。

## 紧凑 token 原型

原路径为每个内部 batch 构建带 padding 的二维 token 张量，再进行 Embedding 和带 mask 的均值池化。原型仍用同一个 tokenizer 和权重，但将 token ID 紧凑拼接，用 `embedding_bag(mean)` 直接生成每句向量。原型只在本目录中，未改生产实现。

| token 数 | 原纯编码 / 紧凑编码，batch 128 | 原 TensorFrame / 紧凑 TensorFrame |
|---|---:|---:|
| 0–63 | 14.0 / 5.7 ms | 19.3 / 10.7 ms |
| 64–127 | 24.2 / 10.7 ms | 30.5 / 15.8 ms |
| 128–255 | 34.5 / 16.2 ms | 41.7 / 21.7 ms |

纯编码每组交替运行 9 次取中位数，再对 3 组取中位数。完整 TensorFrame 对每组各冷运行一次，表中为 3 组中位数。完整冷转换加速约 1.8–1.9 倍，且每组输出与原实现通过 `rtol=1e-4, atol=1e-5` 校验；最大绝对差小于 `1e-6`。余下主要耗时仍在 Python tokenizer，128–255 桶的紧凑路径中约 14.3 / 16.2 ms。

## 解释和下一步

这一轮支持先试紧凑 token 计算。它对首次编码有直接收益，而且在 TensorFrame 路径中也保留下来。下一步应先把该实现作为受限的 CPU/GloVe mean pooling 实验开关接入 v2，再在完整 Arxiv 任务上比较吞吐、内存、模型输入数与预测精度；这一步的单进程采样不能代表整个训练流水线。

对热路径，当前共享缓存已经批量 `index_select` 取向量；`text_expand` 很小。因此本次没有继续做批量 gather 候选。若完整任务的缓存命中率明显提高，再单独评估本地缓存逐条 clone、共享锁与 TensorFrame 预处理。

## GPU 池化追测

在一张空闲 RTX 4090 上，用同样的每组 128 条摘要、单 CPU 线程、3 组数据，测 9 次后对组内和组间取中位数。纯池化比较预先装好的词向量；完整编码比较则包含每批 CPU↔GPU 搬运和 CUDA 同步，但不计一次性的 GloVe 权重上卡。结果见 `gpu_results.json`。

| 每组 128 条摘要 | 64–127 token | 128–255 token |
|---|---:|---:|
| CPU 池化，16 个内部小批次 | 8.1 ms | 12.0 ms |
| GPU 池化，16 个小批次且数据已在显存 | 2.6 ms | 2.6 ms |
| 原 CPU 整段编码 | 24.1 ms | 34.6 ms |
| CPU 查词，GPU 池化，内部 batch 8 | 22.0 ms | 31.2 ms |
| GPU 查词与池化，内部 batch 8 | 17.7 ms | 24.4 ms |
| GPU 查词与池化，一次 batch 128 | 12.2 ms | 18.5 ms |
| CPU 紧凑 token，一次 batch 128 | 9.9 ms | 16.1 ms |

单独看池化，GPU 确实快约 3–5 倍；只把池化迁到 GPU，整段编码却只缩短约 10%，因为分词仍在 CPU、查词结果需要逐小批次上卡、每次执行需同步。将 GloVe 权重常驻 GPU 并合并成 batch 128 后明显改善，但这轮仍慢于 CPU 紧凑 token。GloVe 权重常驻需要约 458 MiB 显存，首次搬运在本机约 0.23 秒。该实验没有与训练共享 GPU，也没有测多进程数据通路，因此不代表训练时的收益。

分桶候选数为 0–63: 5,012，64–127: 12,601，128–255: 2,638，256–511: 1，512 以上: 0。128–255 桶抽中的最高 token 数为 182；唯一 256–511 样本为 262 token。因此更长文本没有足够样本估算吞吐，稀有单条结果仅用于功能检查。SQL 读取、候选分桶和训练不计时；测试只覆盖 `Abstract` 一列及单线程 CPU，不能把这里的倍数当作完整 RelConnector 训练加速倍数。计时器嵌套，不能相加。
