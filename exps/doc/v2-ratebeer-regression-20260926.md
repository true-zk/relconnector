## 22:55 新故障与共享缓存发布竞争修复

诊断长跑在 epoch 0、实际 batch key 7371、已完成 7371 批时失败，断言位于 TimestampEncoder 的 cyclic range 检查。监督脚本按设计退出，没有自动重试。CPU 输入已完整保存至 `benchmarks/v2-full-matrix-20260925/failed-inputs/epoch-0-batch-7371-1790434535893658972.pt`。

保存输入中，`availability.created_at` 第 1315 行、node ID 117418 的编码是 `[2025, 1, 1, 6, 23, 47, 357680]`；SQL 原值是 `2025-02-02T23:47:44.120000`，正确秒值应为 44。原数据合法，异常出现在组装后的特征中；不是需要截断或过滤的数据问题。

代码排查发现共享 encoded cache 的发布竞争：`EncodedFeatureCache.put` 切片创建私有 CPU storage，先将 entry 放进索引，释放锁，再由 manager RPC 序列化返回值。PyTorch 的 `ForkingPickler` 在首次发送时调用 `_share_fd_cpu_()`，会原地搬迁 storage。另一个 manager 请求线程此时已经可以对该 entry 做索引读取，原生索引操作释放 GIL，因此可能持有已经被释放的旧地址。

独立协调复现脚本 `benchmarks/ratebeer-regression-20260926/reproduce_publication_race.py` 同时触发真实 `_CacheOwner.lookup_many` 和 put 返回 entry 的 RPC 序列化：修改前 `before_shared False`，读线程在 TensorFrame 索引处发生 segmentation fault，另一线程正位于 `_share_fd_cpu_`；修改后 `before_shared True`，相同脚本结束且 `reader_errors []`。证据分别在 `publication-race-before.log` 和 `publication-race-after.log`。一般并发压力测试未触发错误，因此采用协调复现而非仅依据随机短测。

修复：仅共享缓存 owner 启用 `share_memory=True`，在发布 entry 前、仍持有缓存锁时完成 node IDs、全部 TensorFrame feature storage（包含 MultiTensor values/offset）和 target 的共享。之后 RPC 序列化不再搬迁已发布 storage。局部缓存默认行为不变，没有将坏值 clamp、跳过样本或修改训练数据。新增回归测试检查所有已发布 storage 在序列化前后地址不变，并验证返回行内容；与已有多进程、稀疏查询、淘汰测试共 4 项通过。

这证明并修复了可导致特征损坏的并发缺陷，与本次非法秒值相符；初次 CUDA 故障没有保存输入，仍不能直接确认它也是同一条触发链。完整 Ratebeer 仍须重新跑完两轮，不能把局部复现通过当成完整 benchmark 成功。
