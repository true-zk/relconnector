# Stack：根据历史映射抖动优化持久化向量布局

## 用于论文和PPT的平均每batch口径

主指标为流水线总时间除以完成批数。Stack两次重复的平均值为 **428.6→370.6 ms/batch，降低13.52%**。整次运行逐批摊销为479.1→421.4 ms/batch，降低12.04%，单独保留启动及其他流水线外开销。

每次完成200批，两种配置各重复两次；包括流水线内部启动、等待与排空，不是独立单批延迟或严格稳态指标。已有初始化产物复用，Stack离线整理另计。精确值和运行标签见[targeted-batch-results-20260927.json](targeted-batch-results-20260927.json)。


## 结论

历史诊断定位到持久化文本向量的分片过多，超过每个工作进程的映射缓存容量。离线合并有效向量后，在同一逻辑缓存、相同模型与采样配置下，预热后的200批训练总时间 **95.81→84.28秒，减少12.04%**；流水线时间减少13.52%，磁盘文本查询累计工作进程时间减少53.59%。这不是改变文本缓存命中率所得的收益，也不是使用更少的训练样本。

一次性合并及全量校验花费144.43秒，单次200批运行不能摊平这项成本；本实验支持反复训练时的布局优化，尚未测量包含整理成本的完整长训练净收益。新增工具生成独立缓存，未覆盖历史缓存，也未改变所有数据集的默认缓存位置。

## 1. 历史证据与代码核对

最终历史Stack实验中，四个组装进程累计磁盘文本查询6374.0工作进程秒，主进程等待就绪batch1841.1秒。四个进程分别打开3,970,438、3,951,469、3,961,300、3,966,650次映射，而每个进程只能保留1,024个映射，淘汰数几乎等于打开数。

已有代码 `_load_many` 已经按分片分组读取，因此新增“按分片批量访问”并不是有效的新方案。实际历史向量目录包含79,587个文件，其中79,583个小于单个标准分片容量。新版写入器会顺序填充分片，但不能修复历史布局遗留的小文件。

## 2. 优化方法与适用条件

从SQLite索引的一致性只读快照读取有效文本键及其向量位置，按旧分片和行号排序，顺序复制到每片8,192行的新布局。每批写入后立即从新位置回读，逐字节比较；再按文本键排序批量构建新SQLite索引，检查行数和数据库完整性。保留原namespace和300维float32向量，不重新编码文本、不修改训练语义。

对于有效向量数N、分片容量R、每进程映射数上限K：

\[
F_{new}=\lceil N/R\rceil.
\]

工具的保守候选筛选条件为：

\[
F_{old}>K,\quad F_{new}\le K,\quad F_{old}/F_{new}\ge4.
\]

条件依据物理布局，而非数据集名称。它只是整理候选筛选，还需验证磁盘查询是否位于关键路径。对没有新增分片且每进程只访问此namespace的静态快照，如果合并后分片集合能放进映射缓存，p个进程的总打开次数满足：

\[
N_{open}\le pF_{new}.
\]

本次N=2,891,661，R=8,192，K=1,024，p=4，得到353片及1,412次打开的上界。保留同一映射上限即可避免容量淘汰。减少的是文件映射管理工作，并非向量内容大小。

## 3. 实验控制与预热校正

两种布局都使用本轮开始时的源码快照，不混入缓存前移候选。固定rel-stack/user-badge、同seed、512 batch size、两层128邻居、128 channels、4个组装进程、严格训练顺序、共享编码缓存2GiB及自适应文本缓存512MiB，磁盘文本缓存开启。两轮各100批，共200批、102,400样本、2,450,293次窗口内唯一行请求。每次从相同逻辑快照建立独立索引，向量文件以硬链接引用不可变数据。

所有训练运行的磁盘缺失、磁盘写入、文本模型输入均为零。索引对应的2,891,661条向量全部在整理时完成字节校验。损失均为有限值，约0.1052；这不是收敛或精度对比实验。

初始化使用同一份已准备统计和拓扑产物；本表不是重新冷建数据库、统计及拓扑的耗时。复制与读取会预热系统文件缓存，因此不将其称为冷磁盘实验。第一轮基线SQL耗时明显偏高，故不以首次134.88→83.44秒作为主结论。主对照在追加确认前确定为B2→A2→A3→B3，每种布局两次，所有记录均保留：

## 4. 稳定状态结果与解释

| 指标 | 原布局均值 | 合并布局均值 | 降低 |
| --- | ---: | ---: | ---: |
| 总时间 | 95.81s | 84.28s | **12.04%** |
| 流水线时间 | 85.72s | 74.13s | 13.52% |
| 等待就绪batch | 58.20s | 46.79s | 19.61% |
| 磁盘文本查询，累计工作进程秒 | 118.30s | 54.90s | **53.59%** |
| 特征转换，累计工作进程秒 | 214.33s | 167.60s | 21.80% |
| SQL，累计工作进程秒 | 24.46s | 24.08s | 1.54% |
| 映射打开数 | 238,288 | 1,312.5 | **99.45%** |
| 映射淘汰数 | 234,192 | 0 | 100% |

工作进程计时存在并行和嵌套，例如文本查询处于特征转换中，不能把这些行相加解释总时间。SQL基本不变，而映射打开、文本查询、就绪等待共同下降，支持布局整理是主要提速来源。查询减少53.6%没有变成总时间减少53.6%，说明剩余特征构造、其他缓存操作和训练仍然存在。

## 5. 成本、资源与结论边界

- 一次整理及全量校验144.43秒，另需新索引与向量副本磁盘空间；保留原目录便于回退。按此次每个200批运行节省11.54秒计算，约需13次相同工作量运行摊平整理时间。这是基于实测窗口的估算，不是完整训练实测。
- 分片合并不缩小float32向量载荷。保留更多文件映射可能增加进程可见的驻留文件页；同一文件的物理页可以被多个进程共享。现有benchmark的peak_rss_mb只测主进程，不能证明全进程RSS或PSS不变。本轮不报告内存改善；内存预算紧张时需补测进程树PSS和文件页驻留。
- 合并工具本身只保留8个源映射、2个目的映射，按8,192条向量分批处理，不将全部向量装进堆内存。
- 已实现静态布局筛选和显式离线工具，没有实现训练期间自动迁移，也没有默认切换其他数据集。Amazon和Trial只能作为候选，需先检查布局和诊断。
- 本实验每版本两次稳定对照，属于200批验证；不能替代完整矩阵，也不宣称获得统计显著性或模型精度提升。

## 6. 工具与复现材料

生产工具：`relconnector_v2/relconnector_v2/features/compact_disk_text.py`。在仓库根目录运行：

```bash
PYTHONPATH=relconnector_v2 ../.venv/bin/python -m relconnector_v2.features.compact_disk_text SOURCE.sqlite --plan
PYTHONPATH=relconnector_v2 ../.venv/bin/python -m relconnector_v2.features.compact_disk_text SOURCE.sqlite NEW_CACHE_ROOT/text_embeddings
```

目标目录必须不存在；工具写入完成前保留INCOMPLETE标记，不应使用该目录训练。错误不会覆盖源缓存。训练通过现有`--cache-dir NEW_CACHE_ROOT`选择新缓存；完整初始化产物需要在该根目录准备，短实验复用已验证产物不等于生产自动跳过初始化。

原始材料：

- `benchmarks/v2-stack-compaction-20260927/compacted-cache/text_embeddings/compaction.json`：全量字节校验、条目数、文件数、整理耗时。
- 同目录下`stack-*.jsonl`、`stack-*-command.json`、`stack-*.log`：原始结果、精确命令、源码及统计driver校验和。

- `host-load.jsonl`、`host-load-confirm.jsonl`：主机负载记录。测试及整理过程均未与正式GPU对照并行。
