# HM v2 退化诊断与修复（2026-09-25）

十任务矩阵已按要求停止；这里只运行 HM 的定向对照和修复验证。

原矩阵的 HM 两轮共 14,972 batch、端到端 5050.8 秒，平均 0.337 秒/batch；
历史 v1 是单轮 7486 batch、1743.1 秒，平均 0.233 秒/batch。
这是不同日期和实现配置的吞吐对比，不能单独证明具体组件的因果影响。

原矩阵中，训练进程等待 ready batch 共 3348.9 秒，占流水线 4603.0 秒的
72.8%。4 个组装 worker 的文本模型编码合计约 31 秒；HM 的自适应磁盘文本缓存
未激活，所以磁盘编码缓存并非退化原因。共享编码特征缓存的 `article` 命中率
为 99.77%，而 `customer` / `transactions` 分别只有 7.30% / 5.98%。
原实现每次共享缓存命中都把整块 TensorFrame 经 manager RPC 返回，即使请求只
需要其中少数行；缓存逐渐积累后，第二轮在跨进程传输及重建上的代价增大。

分别比较流水线时间与端到端时间，不能把初始化缓存命中算成代码加速。

原共享实现的 `article` 查询在短实验中累计占 148.6 CPU 秒；只传命中行后为
58.6 CPU 秒，本地缓存后为约 3.8 CPU 秒。完全关闭编码特征缓存超过 7 分钟
仍未完成同一短实验，说明不能简单禁用缓存。8 worker、总计 2 GiB 的本地缓存
在同一短实验中也超过 4 worker 的完成时间，因此没有继续全量运行。
四组完成的短实验都训练了 512,000 个样本，平均 loss 在 0.4697–0.4701
之间；`ready` 顺序允许异步 batch 次序不同，所以 loss 不要求逐位一致。

修复包括：共享缓存只返回命中行；增加可选 worker 本地缓存并在 HM 验证矩阵
使用 4 worker / 总计 4 GiB；修复本地缓存淘汰最后一个同表块时遗失索引的
`KeyError`；记录逐轮 ready 等待及编码缓存 RPC 耗时。第一次完整复测在同机
外部定时作业启动 12 个满核 worker 后停止，未作为性能结果；待 CPU 负载恢复后
已重启。

完整 HM 复测成功完成 14,972 batch / 7,665,384 个样本：

| 指标 | 原共享 2 GiB | 修复后本地总计 4 GiB | 改善 |
| --- | ---: | ---: | ---: |
| 端到端 | 5050.8 s | 1760.1 s | 2.87× |
| 两轮流水线 | 4603.0 s | 1756.3 s | 2.62× |
| 第一轮 | 1781.9 s | 875.0 s | 2.04× |
| 第二轮 | 2803.2 s | 866.7 s | 3.23× |
| 等待 ready batch | 3348.9 s | 481.9 s | 6.95× |
| 等待占流水线 | 72.8% | 27.4% | — |
| 流水线中非等待时间 | 1254.1 s | 1274.4 s | 基本不变 |

新旧两轮的 batch、样本数一致；模型输入 401,373 / 401,707，模型编码耗时
均约 31 秒。交易表 SQL 执行累计约 892 / 883 CPU 秒，也基本不变。因此
主要收益确实来自减少编码特征缓存的跨进程传输，使训练端不再长期等 ready
batch，而不是减少文本模型编码、SQL 查询或训练工作量。修复后的两轮耗时
875.0 / 866.7 秒，原来的第二轮异常变慢已消失。

这次修复后完整复测命中既有 schema / topology 初始化缓存，流水线外只用
3.8 秒；原矩阵首次初始化为 447.8 秒。端到端 2.87× 包含这部分缓存状态
差异；只看流水线是 2.62×。若粗略把原矩阵的 447.8 秒初始化加到新流水线，
则修复后约 2204.0 秒、仍比原矩阵快 2.29×。这只是启动成本校正估计，
不是同条件冷启动实测。

历史 v1 为单轮 1743.1 秒 / 7486 batch。修复后本轮按两轮总时间换算
为 0.118 秒/batch，历史 v1 为 0.233 秒/batch，观测吞吐约快 1.98×；
加入上述旧初始化成本后估算约快 1.58×。跨实验比较受缓存状态和运行时
负载影响，优先采用上面的同实现前后流水线指标判断修复效果。
