# Ratebeer：低复用任务的编码缓存位置消融

## 用于论文和PPT的平均每batch口径

主指标为流水线总时间除以完成批数。Ratebeer两次重复的平均值为 **1104.6→980.2 ms/batch，降低11.26%**。整次运行逐批摊销为1286.7→1045.9 ms/batch，降低18.71%，单独保留启动及其他流水线外开销。

每次完成64批，两种配置各重复两次；包括流水线内部启动、等待与排空，不是独立单批延迟或严格稳态指标。已有初始化产物复用，Stack离线整理另计。精确值和运行标签见[targeted-batch-results-20260927.json](targeted-batch-results-20260927.json)。


## 结论

针对历史编码缓存查询和发布成本高的问题，在相同2GiB总预算下，把共享编码缓存换成四个工作进程各512MiB的本地缓存。预热后的64批短实验中，原读取路径的总时间 **82.35→66.94秒，减少18.71%**；流水线时间 **70.69→62.73秒，减少11.26%**。总时间还包含流水线之外的启动和管理开销，不能把18.71%全部称为稳态吞吐提升。

“先查询编码缓存、再向SQL读取缺失行”的新增候选，在本地缓存基础上只再改善0.87%，因此不保留此代码。此次有效选择是针对低复用、高跨进程成本任务使用现有本地缓存能力；不是声称实现了新的自动缓存切换算法。

## 1. 为什么选择这个瓶颈

历史完整Ratebeer任务中，编码缓存命中约19.9%，但累计查询6179.4、发布8984.1工作进程秒，主进程等待就绪batch11389.2秒。大事实表的重复利用有限，共享owner仍需要处理所有查询和发布。

本次共享基线的整体编码缓存命中约16.5%，`beer_ratings`主表只有约4.1%。这一观察和历史低复用模式一致。要验证的假设是：共享带来的额外复用不足以抵偿进程间通信与同步。不能仅根据共享命中率高于本地就认定共享更快。

## 2. 实验设计和预热处理

同一rel-ratebeer/beer_ratings-total_score任务，同seed、同已准备schema和拓扑、batch size512、两层128邻居、channels128、4个固定组装进程、严格训练顺序。两轮各32批，共64批、32,768样本，窗口内唯一行请求累计7,149,534。编码缓存总预算都为2GiB，自适应共享文本缓存512MiB，磁盘文本缓存关闭。每次启动独立进程及进程内缓存。

A表示原源码+共享缓存；B表示缓存前移候选+本地缓存；C表示原源码+本地缓存。原源码是本轮开始时工作区快照，保留上一轮已接受优化。所有精确命令和源码哈希都随结果保存。

首个A3为139.37秒，SQL累计253.45工作进程秒；后续共享A4为82.76秒，SQL54.91秒。首次访问原数据库明显受到文件页预热影响，因此不能将139.37→66.41秒写成代码使训练“快一倍”。追加消融前确定用A4/A5、B4/B5、C1/C2作为预热对照。

## 3. 消融结果

| 指标（两次均值） | 原路径、共享 | 原路径、本地 | 缓存前移、本地 |
| --- | ---: | ---: | ---: |
| 总时间 | 82.35s | **66.94s** | 66.36s |
| 流水线时间 | 70.69s | **62.73s** | 62.18s |
| 等待就绪batch | 58.02s | 50.25s | 49.52s |
| 编码缓存查询，累计工作进程秒 | 22.38s | **2.17s** | 2.20s |
| 编码缓存发布，累计工作进程秒 | 36.64s | **8.93s** | 8.87s |
| SQL，累计工作进程秒 | 55.02s | 54.67s | 53.19s |
| 特征转换，累计工作进程秒 | 70.55s | 86.62s | 86.90s |
| 编码缓存命中率 | 约16.5% | 约1.6% | 约1.6% |

本地缓存确实损失了跨工作进程复用，编码转换时间因此增加；但缓存查询和发布下降更多，主进程等待和流水线都缩短。SQL基本保持同一量级，支持缓存位置是主要改善原因。

缓存前移在本地路径基础上总时间只减少0.87%，不作为新优化成果。此前Avito共享模式中，这个候选虽让SQL返回量减少81.56%，总时间仅减少0.17%。这两组消融共同说明：去掉局部重复工作必须和关键路径结合验证，不能仅看SQL或命中率。

累计工作进程计时包含并行和嵌套，不应相加为总时间。几次运行文本模型输入约26.36万，因共享预留与并发调度存在小量差异；没有缩减采样请求或训练样本。所有运行完成64批，loss有限且约0.5729；本次不是模型收敛验证。

## 4. 代码取舍和使用方法

缓存前移的三个生产文件已经按本轮起始工作区快照恢复：`features/assembler.py`、`features/process_worker.py`、`features/sql.py`。新增候选测试随完整候选一并归档；此前的行选择、时序语义、共享缓存修复等不受影响。归档位于`benchmarks/v2-cache-before-sql-20260927/candidate/`，还保存差异、68项测试通过记录及真实Avito特征逐值等价记录。

Ratebeer本地配置使用现有参数：

```bash
--encoded-cache-scope local --encoded-cache-mb 2048 --assembly-processes 4
```

该预算是整个组装进程池的预算，平均每个进程512MiB。没有新增按名称自动切换的算法，也没有立即更改完整矩阵中Ratebeer的默认配置：64批尚未覆盖长训练的缓存饱和、事实表工作集演化和自适应worker调度。下一步应按该候选配置验证更长窗口，再决定默认选择。

## 5. 原始材料与局限

- `benchmarks/v2-cache-before-sql-20260927/ratebeer-controlled-summary.json`：三个组别的均值、范围、流水线与整体降幅。
- 同目录`ratebeer-*.jsonl`及`ratebeer-*-command.json`：所有运行、固定源码和精确命令；A3探索结果仍保留。
- `run_ratebeer_series.py`、`run_ratebeer_ablation.py`：顺序执行脚本，测试和其他GPU任务未与本轮计时实验并行。
- `production-disposition.json`：恢复的三个源码文件哈希及候选归档说明。
- `host-load-ratebeer*.jsonl`：主机负载记录。此为共享主机重复验证，每组两次，不宣称统计显著性。

这是已准备初始化后的短程预热实验，不能替代历史两轮最多20,000批的完整任务结果。本次没有证明进程树RSS下降；现有benchmark的RSS字段只包含主进程。完整验证还需要进程树RSS/PSS、较长缓存压力和稳定吞吐观测。
