# Vanilla、v1、v2 十数据集性能图解释

## v1 与 v2 的区别

v1 是基于单进程的数据准备优化版本，通过节点去重、跨批次窗口、缓存复用和进程内线程流水线减少重复读取与编码。实际训练进一步暴露出 assemble（特征读取、编码与批次组装）的供给瓶颈：即使减少重复工作，数据准备仍可能跟不上 GPU 消费。v2 因此升级为多进程架构，将采样、assemble 和训练拆分为独立的执行阶段，分别由采样进程、组装进程池和训练主进程承担，通过有界队列连接并重叠执行。这里的单进程不等于单线程，多进程也不改变邻居采样与模型训练的算法语义。

本报告沿用历史实测及已选定 v2 复测记录，未采用内存估算。原 v1 在展示中统一称为 v1（single process）；v2 标为 multi process。图已去掉底部小字，测量条件保留在 PPT 备注、解释页和本文件中。

## 如何解释整体趋势

Vanilla 已有异步线程和 raw cache，并非纯串行或完全无缓存。它仍经常重复读取/转换节点特征、重复执行文本编码，CPU 特征供给容易落后于 GPU 训练。v1 的主要改进是节点去重、跨 batch 合并特征请求和文本缓存：先减少需要做的工作。v2 则将采样、SQL/编码/组装、训练组织为独立进程流水线，并按成本选择共享/本地编码缓存、本地文本槽位索引和持久化 embedding；在复用生效后继续降低缓存查询、锁与跨进程传输开销。

这些机制解释了观测趋势，但各项没有都做隔离变量的 A/B。历史与 v2 的 epoch 数、缓存状态、实现修订不同，图中的时间是含准备的秒/batch。下表倍率是 v1/v2，不表示所有收益来自多进程或某一单项算法。

## 按数据集类型解释

以数据特征和主导瓶颈分类，而非逐个数据集复述。类别可以重叠，括号中的数据集仅为代表性证据。

### 文本编码重、可跨轮复用（Arxiv / Amazon / Stack）

瓶颈：长文本与大词汇集合使重复编码昂贵，GPU 等待特征。

策略：直接文本编码＋并行组装；适合时持久化 embedding，跨轮复用。

证据：Arxiv 两轮模型输入 184,724 → 1,316；部分收益来自既有热缓存。

### 复用率高、缓存命中成本高（Salt / HM / Trial）

瓶颈：减少编码后，共享查询、锁竞争和跨进程传输成为主要成本。

策略：本地槽位索引、批量取向量、只传请求行；必要时用 worker 本地缓存。

证据：HM ready 等待 3,348.9 → 481.9 秒；本地缓存为显式配置。

### 读取量大、特征供给仍重（Ratebeer / Avito）

瓶颈：SQL 读取与组装成本高，未命中的绝对编码量仍可很大。

策略：采样 / 多进程组装 / GPU 训练重叠；缓存路径按实际复用成本选择。

边界：Ratebeer 第二轮仍编码约 2,050 万条；更快不等于消除供给瓶颈。

### 数值宽表、初始化占主导（Event）

瓶颈：列多、逐列扫描与排序重复；少量训练无法摊薄初始化成本。

策略：按行数和内存预算分组扫描，精确 partition 分位数，复用初始化产物。

证据：冷初始化 2,164 → 606 秒（3.57×）；图中 49.83× 包含热初始化收益。

### 小数据集、固定开销占主导（F1）

瓶颈：启动、进程协调和队列开销，相对实际训练工作量更突出。

策略：避免不必要的磁盘缓存；当前通用流水线收益有限，少 worker 是后续方向。

证据：图中 v1 / v2 仅 1.13×；不能预期小数据集获得与重文本任务同等收益。

共同逻辑：减少重复工作 → 降低缓存命中成本 → 并行提升供给；初始化按内存预算处理，小数据集则受到固定开销限制。

机制解释不等同于每项均有独立A/B，worker计时也不能相加为墙钟耗时。

## Ratebeer：为什么前两个超时，而 v2 有成功结果

### 1. 先核对完成条件

| 版本 | 目标 / 实际规模 | 结果 |
|---|---|---|
| Vanilla | 历史完整1轮目标20,743批；当前报告没有可靠的完成批数 | 14,400秒终止，超时 |
| v1 | 历史完整1轮目标20,743批，实际完成15,686批 | 14,400秒终止，完成75.6% |
| v2 | 每轮最多10,000批，实际完成2×10,000批；不是完整两轮遍历 | 15,444.93秒成功退出，即4小时17分25秒 |

因此不能说“v2在相同4小时预算内完成了前两者无法完成的完整两轮”。它运行超过4小时，每轮又截断到10,000批，第二轮还重复遍历选定规模，不能当作20,000个不重复批次的完整单轮。

按已观察吞吐折算：v1为14400/15686≈0.918秒/batch，v2为15444.93/20000≈0.772秒/batch，v1/v2≈1.189，单位batch耗时减少约15.9%。这是跨实验吞吐估算，不是严格同条件配对结果。Vanilla没有完成批数，无法从TO标记推导确切倍数。

### 2. 性能收益是什么

Ratebeer训练规模大，持续的SQL读取、文本编码与特征组装使旧在线方案难以在4小时完成完整轮次。v2让多个assembly进程并行处理CPU工作，并与采样和GPU训练重叠，改善了供给吞吐。当前日志仍有11389.2秒ready等待，说明瓶颈并未根除。

本轮累计内存文本命中率约88.7%，没有触发当前低命中率磁盘缓存门槛，磁盘文本缓存保持关闭。尽管比例看起来较高，剩余未命中的绝对工作量依然很大：两轮文本模型输入分别20,245,311和20,503,129条。因此不能解释为“第二轮不再编码”或“磁盘缓存消除了Ratebeer瓶颈”。这些计数不是全局唯一文本数量；当前证据也不能证明关闭磁盘一定最优。

### 3. 稳定完成与性能优化是不同证据

v2此前发生过共享编码缓存发布竞争：缓存条目先被其他请求看到，而首次RPC序列化随后搬迁storage，可能使并发读取访问旧地址，导致特征损坏。修复将共享存储准备放在发布之前，最终通过20,000批长跑和完整性审计。

这说明修复支持本次配置稳定完成，是正确性/稳定性结果；不能独立作为1.19倍加速的原因。第一次故障缺少输入现场，仍无法证明两次故障完全同源。

适合汇报的表述：**“Ratebeer仍受SQL与文本供给限制。v2的观测吞吐比v1约快19%，并在缓存并发修复后稳定完成2×10000批；由于运行规模和预算不同，不能把TO与成功直接解释为同条件下的完成能力突破。”**

## RSS 的解释

所有RSS点均沿用历史记录，v2空心点仅是训练主进程RUSAGE_SELF峰值；组装、采样和manager内存不在内。图可以展示记录值，不能用它断言三者总内存相近，或把主进程差异解释为整体内存节省。超时版本RSS仅为截至终止的观测峰值。
