# v2 ROI 缓存：十库 5×100 batch 实验

## 结论

本次十库正式运行全部完成，0 个失败。协议为固定回放、5 个 epoch、每轮最多 100 个 batch；F1 每轮实际只有 6 个 batch，Event 每轮实际只有 38 个，其余八库均为 100 个。所有训练使用 4 个 assembly worker、严格顺序、关闭跨 epoch 预取，并从空文本缓存开始；schema/拓扑在回放准备后复用。

ROI 相对同一固定回放的“全关缓存”历史对照，总训练时间从 3992.15 秒降到 2739.55 秒，减少 31.4%。十库中 7 个更快；F1、HM、Event 分别慢 3.8%、3.0%、9.2%。因此，当前结果支持“ROI 对大部分库有收益且能限制磁盘占用”，但还不支持“所有数据集都不劣化”。这三个回归项都是短训练或快速编码数据集，下一步应给磁盘缓存增加更保守的最小绝对收益门槛，并用独立重复实验判断 3% 左右差异是否只是运行波动。

与用户附件旧图做机械比较时，按本次实际 batch 数加权，均值从 1.287 降到 0.649 秒/batch，表面减少 49.6%。这个数字不能作为论文主结果：附件中的 Event v2 为约 15.9 秒/batch，包含重冷初始化；本次 ROI 训练指标不含单独的 654.25 秒回放/初始化准备。移除 Event 后，附件口径的加权结果反而慢 11.6%。旧图来自完整数据集、不同 epoch 数和不同缓存状态，固定 100-batch 运行又显著放大 worker 启动成本，因此这里只能逐库、方向性参考。

Amazon、Stack、RateBeer 的后四轮收益最明显。Amazon 从首轮 103.23 秒降至热轮均值 12.04 秒；Stack 从 102.99 降至 22.61 秒；RateBeer 从 134.98 降至 65.80 秒。这直接支持慢文本编码在多 epoch 下落盘复用。Avito 只写入 313 个磁盘 block，仍基本保持图中速度，说明 ROI 确实能在编码快的库上抑制大规模落盘。

Salt 和 Arxiv 说明当前策略还有边界。两者相对同协议全关缓存分别快 22.6% 和 22.6%，但相对旧图的完整长跑却慢很多，因为 100-batch 协议放大了启动和冷轮成本。Salt 的首轮到热轮只减少 8.9%，同时整树 PSS 达 42.64 GiB；其主要问题已经不只是文本重算，还包括大表组装、worker 本地对象和供给路径。

## RSS 口径

附件旧图的 v2 RSS 是 `RUSAGE_SELF` 主进程高水位，不包含 sampling、assembly worker 和 manager。本次保留三项指标：

1. benchmark 内的主进程峰值 RSS，用于与旧图同口径比较；
2. 每 0.5 秒采样的进程组 RSS 求和，这是会重复计算共享页的上界；
3. 每 1 秒采样的进程组 PSS 求和，共享页按进程分摊，更接近整棵进程树实际物理内存。

同口径主进程 RSS 十库均下降：算术均值从附件的 2.758 GiB 降至 2.178 GiB，下降 21.0%，各库下降 15.6%–24.9%。但这个结果不能解释为 v2 总内存只有约 2 GiB。整树 PSS 的中位数为 9.24 GiB、均值 14.18 GiB，范围 7.54–42.64 GiB；整树 RSS 求和的中位数为 10.96 GiB、均值 15.99 GiB。Salt、Arxiv、RateBeer 的整树 PSS 分别为 42.64、22.90、15.86 GiB，是后续内存优化的主要对象。
