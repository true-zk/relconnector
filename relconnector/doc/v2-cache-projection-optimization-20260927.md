# v2 共享缓存投影优化尝试（2026-09-27）

## 结论与代码状态

本轮完成了两个候选改动及实际 GPU 训练对照，但没有确认端到端提速。Salt 四次交错实验中，编码缓存查询累计工作进程时间平均减少 18.90%，benchmark 总时间却从 128.32 变为 129.30 秒（增加 0.76%）。两次/版本且存在外部 CPU 竞争，不能据此认定候选稳定退化，也不能宣称整体加速。

**未将本轮候选保留为默认实现。** 三个生产源文件已恢复为本轮开始时的源码，上一轮已验证的专用行选择和缓存形状修正均保留。候选代码、测试、补丁和结果完整保存在 `benchmarks/v2-cache-projection-20260927/`，可独立继续消融。

## 改动与原理

1. 合并共享编码缓存的“各块取行 → 拼接”：对 CPU 稠密数值、类别、时间张量和定宽文本向量，只分配最终输出，各块直接通过 index_select 写入对应区间。变长列、梯度输入、空特征及其他不兼容情况保留原路径。
2. 接收端确认缓存结果已经是完整、顺序、紧凑的行集时，复用这个结果，省掉第二次相同取行。部分命中的请求位置仍保留，并在与未命中行合并后恢复请求顺序。请求前缀或乱序块不能误走快捷路径。

改变的是特征复制和物化次数，不改变邻居采样、时间约束、文本归一化、向量精度或模型。融合取行的输出独立于源缓存；接收端仅在只读组装阶段复用结果，最终 batch 行展开仍产生独立特征。稠密输出的中间缓冲减少不代表进程 RSS 按相同比例减少，本轮不作作业级内存结论。

## 实验设置

基线 A 是本轮开始时、已经包含上一轮行选择优化的 v2；不是 Git HEAD，也不是历史 vanilla/v1。候选 B 包含上述两个改动。Salt / item-incoterms，2 epoch × 30 batch，batch=512，fanout=128,128，channels=128，seed=42。RTX 4090 物理 GPU 1，Torch CPU 单线程，固定 4 个组装进程、严格消费顺序，共享编码缓存 2 GiB、adaptive 文本缓存 512 MiB，磁盘文本缓存关闭。每次启动独立进程及内存缓存，复用同一离线初始化缓存。

67 项测试全部结束后，执行 8 批预热，再按 A1→B1→B2→A2 运行；不挑选最快记录。表中总时间来自 benchmark.duration_s，覆盖 model.train() 及其准备阶段，不包含 Python 解释器启动和模块导入。该组结果仅为短时探索，不替代十库矩阵或冷初始化实验。

| 运行 | 实现 | 总时间/s | 流水线/s | 就绪等待/s | 缓存查询/工作进程秒 | 编码缓存命中率 | loss |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| salt-a1 | 基线 | 133.11 | 116.62 | 95.35 | 35.67 | 42.20% | 1.25703465 |
| salt-b1 | 候选 | 131.88 | 114.61 | 92.55 | 25.04 | 41.08% | 1.25713797 |

每次均为 60 批、30,720 样本、104,206 个实际文本模型输入。并发调度影响缓存准入、淘汰和命中量，因此查询时间下降不能全部单独归因于融合复制。loss 有轻微差异，不声称训练逐位确定或最终精度已验证；特征操作的正确性测试要求逐值一致。

## 主机负载与结论边界

实验启动前 GPU 空闲；运行期间另有用户启动 CPU 训练任务。人工检查发现第一轮基线期间已有这些作业，随后启动每 10 秒一次的轻量负载记录。持续记录未覆盖 A1，B1 也缺少开头，不能声称全部运行受到相同干扰。

| 运行 | 负载样本数 | 全机 CPU 平均利用率 | 其他进程累计 CPU 平均值 |
| --- | ---: | ---: | ---: |
| salt-a1 | 0 | 未连续记录 | 人工检查发现外部 CPU 作业 |
| salt-b1 | 11 | 85.7% | 1205.4% |
| salt-b2 | 13 | 79.1% | 1113.0% |
| salt-a2 | 13 | 77.5% | 1081.5% |

其他进程累计 CPU 以单个逻辑 CPU 满载为 100%，不是全机百分比。A2 后段外部负载下降；这会影响均值，不能从本组数据提取精确因果加速比。没有停止、限速或修改其他用户作业。本轮选择归档候选，避免将不确定收益写入默认版本及论文正式结果。

## 下一轮按什么顺序做

1. 在主机负载稳定时，对两个候选分别消融，再验证组合；共享缓存收益要计入命中量、返回字节与 RPC 开销。当前不足以设置按数据集名选择的规则。
2. 优先检查文本向量恢复与特征转换。上一轮 Salt 的 text_expand 有 10.41 工作进程秒，当前仍使用 stack 后通用高级索引；可单独试专用行选择或批量取向量。保持文本内容、缓存状态、精度和模型输入量一致。
3. 再依据测得的成本选择共享/本地缓存与稀疏/块读取；所有内存比较固定作业总预算，不能把每个 worker 同样的预算误当成总预算相同。
4. Event 拓扑冷初始化、Arxiv 等持久化文本缓存批量读取继续列为独立实验；本轮没有修改这些路径，不能宣称它们获得新增加速。

完整决策模型、验收条件及数据集方向见 [下一轮优化计划](v2-next-optimization-plan-20260927.md)。

## 复现

目录 `benchmarks/v2-cache-projection-20260927/` 包含 `baseline/`、`candidate/`、`change.patch`、逐次命令/源码 SHA256、JSONL、日志、summary.json、primary-summary.json 和 host-load.jsonl。`run_one.py` 现在明确读取对应冻结快照，不会因默认代码恢复而错误运行基线作为候选。使用新标签，避免覆盖既有结果：

```bash
.venv/bin/python benchmarks/v2-cache-projection-20260927/run_one.py baseline salt-recheck-a1
.venv/bin/python benchmarks/v2-cache-projection-20260927/run_one.py candidate salt-recheck-b1
```

`summarize.py` 的主均值固定取原始四个标签，新增复验需显式设置新的标签组；不得把新旧主机状态的实验任意拼接。候选正确性测试可将 PYTHONPATH 指向 candidate，并用 unittest discover -s 对应 candidate 目录运行归档的 test_row_gather.py。
