## 本轮的结构性问题：缓存命中发生得太晚

旧路径是：节点去重 → 查询所有原始特征 → 解码并重排行 → 查询编码缓存 → 仅对缓存缺失行编码 → 展开为 batch。编码缓存只减少编码，不能避免已经发生的 SQL 与解码。

新路径是：节点去重 → 一次查询编码缓存 → 只读取、解码和编码未命中的行 → 合并命中和缺失结果 → 按原采样顺序展开。命中的行不再重复访问原始特征数据库。缓存预算、准入规则、时序采样、文本精度和训练模型均不改变。

对每张表，请求的唯一节点集合记为 U，缓存命中集合为 H，缺失集合 M=U\H。新路径只向原始读取器提交 M。实际SQL返回量还受已有原始块缓存与密集块过量读取影响，因此不能直接将97.85%的编码命中率当成97.85%的SQL减少率；必须测实际返回行数。

预计节省的是命中部分的读取、解码及原始数据重排成本。新路径仍需一次编码缓存查询，且仍需最终特征展开，不承诺消除RPC或宽向量内存带宽开销。即使编码缓存完全关闭，也保持正常查询和编码语义。

## 正确性约束

- 保存第一次查询返回的缓存对象，直到本次特征合并结束。不能先问“哪些行命中”，执行SQL之后再查一次，否则并发淘汰会使先前跳过的行丢失。
- 命中表示静态行特征可复用，不表示不同seed时间下的采样邻域可合并。拓扑、节点时间、seed时间、标签和逆映射保持原样。
- 多batch特征窗口与推荐任务三个分支共享同一份唯一节点特征，不重新编码同一窗口。
- 新增跳过SQL的行数计数；原始块缓存命中与编码缓存命中分开统计，避免双计缓存覆盖。

## 实验协议

源码基线来自本轮开始时的工作区，位于 `benchmarks/v2-cache-before-sql-20260927/baseline/`，上一轮归档候选未混入。先运行精确值、部分/全命中、重复节点、推荐分支、缓存禁用、缺失ID和淘汰期间引用有效性测试，再运行完整v2测试。

Avito采用同一GPU、固定4worker、严格训练顺序、同seed、共享编码缓存2GiB、文本缓存512MiB，关闭磁盘文本缓存，独立进程内缓存。复用相同离线初始化产物，2轮×250批，按A→B→B→A对照。评估总时间、流水线、等待、SQL执行/解码、SQL返回行、编码缓存命中、实际文本模型输入。性能实验与测试不并行；记录外部负载。只认定真实工作量和端到端均有支持的改善，不靠内核结果替代训练结论。

Ratebeer再用相同配置的较短运行检查低复用情况下的收益或退化。两类数据集均验证后才决定默认保留范围；不按数据集名称硬编码优化开关。

## 深查 Stack：不是缺少批量读取，而是持久化碎片

代码核对发现 `_load_many` 已经按向量分片分组读取，不能将它重复列为尚未实现的新优化。进一步查最终历史诊断，四个 worker 的 `mapping_opens` 分别为 3,970,438、3,951,469、3,961,300、3,966,650；映射缓存容量均为1,024，淘汰次数几乎等于打开次数。

本次只读检查现有 Stack 向量目录：**79,587 个分片，合计 3,469,993,200 字节，其中79,583个小于8,192条300维float32向量的容量**。因此不是简单的向量总字节过大，而是早期小分片遗留造成大量映射反复打开/淘汰。当前追加式写入已经改善新分片布局，但不会自动整理已有文件。

更有针对性的后续实验是离线合并不可变小分片：保持文本hash、namespace、向量逐位不变，生成独立的新索引/向量目录，按8,192或更多行成片。理想有效向量载荷约需353个8,192行分片，低于现有1,024映射预算；实际需要按索引有效行数计算，不直接用目录总字节当有效数据量。然后在原布局/合并布局的相同逻辑缓存快照下重放同一请求，比较映射打开数、磁盘查询、训练等待和墙钟。

不要仅增加 mmap 上限掩盖碎片，也不要直接覆盖运行中的原缓存：先生成独立产物，校验全部键与向量，再做训练对照。此项现已完成独立合并及六次训练验证；历史缓存保持不变，详见下文与独立报告。

## 在线实验中发现的第二个限制

首个 Avito 配对：缓存前移将SQL返回行由12,608,262降至2,306,136，SQL服务时间111.98→19.12工作进程秒；共享编码缓存查询却89.69→120.33秒，写入27.60→45.14秒，总时间128.90→120.71秒。该单次结果仅是诊断：可能是SQL节流减少后更多worker同时访问共享owner，缓存调度与命中量也改变。不能把SQL的83%降幅直接写成训练提速。

因此补充同总预算的共享/本地消融：四worker本地缓存总计2GiB，即每worker512MiB；与共享2GiB比较。希望同时避开命中行SQL与共享owner通信，代价是worker间重复缓存可能降低命中率。先实测，再决定适用范围，不直接宣称自动启发式已经实现。

## Stack 独立存储布局实验设计

先对历史SQLite向量索引做一致性备份；索引引用的已发布向量行不可变，用硬链接建立冻结基线副本；后续写入不得改写这些已发布行，各次训练新写入使用独立文件。再从冻结基线生成独立合并副本，不改历史索引或向量内容。逐项读取有效索引，按旧分片顺序拷贝向量，每8,192行一片；每条向量写入后从新位置回读，要求字节完全相同。最后按文本hash顺序批量构建新索引并校验数据库。

训练对照两边使用同一份本轮开始时的v2源码，即**不混入缓存前移候选**。每次运行都从冻结逻辑快照建立独立索引与不可变向量文件链接，避免前一次训练写缓存影响下一次。固定统计产物、同seed、4worker、同缓存预算、同200批工作量，按原碎片布局→合并布局→合并布局→原碎片布局运行。检查实际模型输入、磁盘命中、映射打开与淘汰、训练工作量、等待和总耗时。离线拷贝/校验会预热文件缓存，因此属于文件缓存较热时的布局比较，不冒充冷磁盘实验。离线合并时间单独报告。

## Ratebeer 验证口径补充

针对历史每轮约20%编码缓存命中，却支付大量共享查询/发布成本的问题，低复用验证比较“原共享2GiB路径”和“缓存前移 + 四worker本地总计2GiB路径”。这是同时改变查询顺序和缓存位置的组合对照，不能把全部收益单独归因于缓存前移。固定2轮×32批的节点请求，A→B→B→A，冻结同一历史统计产物，关闭磁盘文本缓存。报告流水线和端到端，分开观察消除manager启动与在线服务成本，明确它不是完整2×10,000批复验。

## 可复用的方法：让有效分片集合适配映射预算

设不可变向量条目数为 N，每个合并分片容量为 R，每个worker最多保留 K 个映射，worker数为 p。合并后分片数为 `F_new = ceil(N/R)`。本次保守启发式只推荐满足以下条件的整理候选：原有效分片数 `F_old > K`、`F_new <= K`，且分片数量至少减少4倍。它根据实际布局和预算选择，不使用数据集名称。

对这样的静态快照，若每个worker只维护此namespace的映射且没有新增分片，合并后整个运行的打开次数有界：`N_open <= p * F_new`，因为第一次映射后不再因容量不足淘汰。本次Stack为 `N=2,891,661, R=8,192, K=1,024, p=4`，得到353个分片、最多1,412次打开。首个合并布局运行实测1,309次打开、0次淘汰；原布局为239,080次打开、234,984次淘汰。这是工作量的结构性减少，而非索引指令的小幅优化。

启发式只是候选筛选，不保证总训练加速。必须检查实际读取阶段耗时、就绪等待和总时间；整理过程本身也有一次性成本。本次离线整理144.43秒，完整训练是否回本需结合实际节省，不能把离线工作当免费。

### Ratebeer 追加消融与预热控制

首个共享基线SQL累计253.45工作进程秒，后续本地候选只有53.35秒，但实际SQL返回量仅少约1.6%，所以这部分差异主要提示原始数据文件预热，而非缓存跳读本身。不可将139.37→66.41秒直接当最终提速。完成首次A3→B3→B4→A4后，追加原路径本地C1→新路径本地B5→原路径本地C2→原共享A5，以A4/A5和B4/B5验证预热后的组合差异，以C1/C2和B4/B5判断缓存前移是否具有独立价值。各组仍固定64批；最终默认实现取舍以该消融为准。

## 下一阶段选择标准：按成本收益决定，而非只看命中率

对一个特征表，令两种缓存布局各自的命中行数为H、缓存查询时间为L、缓存发布与准入时间为P，避免一次编码的平均成本为C。共享布局相对本地布局更有价值的必要成本比较可写成：

`(H_shared - H_local) * C > (L_shared + P_shared) - (L_local + P_local)`。

该式仅近似比较缓存服务成本，完整流水线还受SQL、展开、采样和GPU重叠影响，最终需以总时间与就绪等待验收。Ratebeer这样大量流式行的任务，不能只因为共享命中率更高就认定共享更快；Salt这样宽向量重复需求的任务，也不能仅因为跳过SQL就认定内存物化变少。

据此，下一阶段优先级为：先完成Ratebeer缓存位置消融并决定是否保留缓存前移代码；再为Amazon补齐缺失的工作进程诊断；对Trial/Arxiv只在确认分片抖动后迁移已验证的布局工具；Event独立验证计数扫描去排序的拓扑等价性和冷初始化耗时；Salt测量重复向量物化与带宽，不再优先微调SQL。每项须报告独立初始化成本、在线关键路径、完整任务工作量和进程树内存，不将局部累计时间直接当总时间。
