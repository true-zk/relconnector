# Stack v2 查询退化诊断与修复（2026-09-26）

按用户要求终止原 Stack 进程及其自动续跑调度，保留已有任务结果。
原 Stack 运行约 5 小时后没有结果；检查时 GPU 利用率为 0%，15 秒采样内
各 worker 的 CPU 时间和读写计数均未增长。未能取得原进程的 Python 调用栈，
所以不能把这次停滞断言为某个已确认的死锁。
进程终止前的状态保存于 `benchmarks/stack-regression-20260926/stopped-processes.json`。

## 已确认的性能瓶颈

以相同 GPU、4 worker、2 epoch × 50 batch 复现原共享文本缓存配置，
通过启动时安装的 faulthandler 获取每个进程的调用栈。
反复看到一个 worker 在共享文本哈希表内查询/发布，其他 worker 等待同一把锁。
缓存只有 447,392 个向量槽，短测内已填满；新文本发生 573,919 次拒绝，
每次未命中最多逐项探测 32 槽。旧实现每次探测都执行 PyTorch 标量索引，
命中时在锁内逐条 clone，发布时也在锁内逐条复制向量。

本次对照磁盘缓存已经启用并复用了原长任务留下的 embedding。
模型编码合计仅 0.74 worker 秒，说明这次慢的主要原因是共享查询/发布，
不能靠增加编码进程或再次编码解决。

## 修复

- 保留跨 worker 的共享向量和编码预约，没有给 Stack 添加策略特判。
- 将哈希计算移到锁外；共享元数据通过零拷贝 NumPy 视图读取，避免逐槽
  派发 PyTorch 操作；spawn 后重新绑定视图，不序列化为私有数组。
- 在锁内只取得不可变的已发布槽地址，再到锁外一次 gather 需要的向量。
  返回值拥有独立存储，调用者修改不会污染共享缓存。
- 发布前在锁外整理/校验向量，锁内批量复制、更新状态及计数。
- 给共享锁获取增加截止时间，避免异常持锁导致无限等待。
- 修复一条独立、确定存在的挂起路径：seed 读取线程异常时，旧代码只设置
  stop，父进程仍等待 ready batch，子进程又等待父进程 release。
  现在异常进入统一 error queue，由训练端抛出并清理进程。
  这条路径用故障注入验证，但没有证据认定它就是原 Stack 停滞的触发原因。
- CLI 默认每 30 秒输出已训练 batch、epoch 和距上个 batch 的时间；
  `--progress-interval-s 0` 可关闭。

## 13:13 长跑停顿：分片映射没有上限

恢复后的 Stack 在 epoch 0 完成 6,614 batch 后，epoch 1 到 2,216 batch 停住（总计 8,830）。监控于 13:13 自动保存所有子进程线程栈。采样端等待 inflight 额度，训练端等待 ready batch，四个组装端均停在 finally 的 release_processes.wait；缓存 manager 当时空闲。旧结果未计入成功成绩，诊断位于 `benchmarks/stack-regression-20260926/stall-1313/`。

进一步检查发现 `_mapped_shards` 原先是无上限的字典，每次遇到新文件就永久持有 np.memmap。已有 Stack 缓存含 2,884,719 条向量，分布在 77,339 个被索引的分片。机器的 `vm.max_map_count` 为 65,530；旧 worker 的 FDSize 都增长至 65,536。诊断复测在启动后约一分钟已有 8,800–9,100 个 embedding 分片文件描述符，数量继续增加。

隔离进程测试成功复现同一资源链：累计 65,411 次映射后出现 `OSError(12, 'Cannot allocate memory')`，随后 `threading.Thread.start` 也报 `can't start new thread`。旧错误通道是 multiprocessing.Queue，第一次报错才启动 feeder 线程；如果此时启动失败，会在设置 stop 之前进入 finally 等待，而主进程没有收到错误。这与现场等待链一致。旧进程没有捕获原始异常文本，因此以资源证据和隔离复现支持该归因，不将旧现场异常文本视为已经取得。

修复内容：

- 磁盘读取使用有界 LRU，默认每个 cache 最多 1,024 个映射；超限前关闭最旧映射。磁盘向量不删除，后续重新打开即可，依旧不需要模型编码。
- 返回向量保持独立副本，关闭映射或整个 cache 不改变已经交给调用者的数据；增加跨分片驱逐、重开、顺序和生命周期测试。
- 错误通道改为同步 SimpleQueue 包装，不需要报错时再启动 feeder 线程；故障注入同时禁止新线程并抛出 mmap 错误，验证主进程能收到错误并清理所有 worker。
- 当所有组装进程已报告完成、训练仍无法推进时明确报错；进度日志增加队列字节数、未完成窗口数及 worker 完成状态。诊断钩子增加 SIGUSR2 对流水线标量状态的采集。

验证：12 项磁盘缓存测试与 6 项流水线测试通过；另有 14,000 个唯一 batch 的两轮合成压力测试通过（58.05 秒；在此次 LRU 修改前完成，用于排除一般批次计数路径故障）。新真实 Stack 短测（2×100 batch）完成：95.11 秒，第二轮训练 27.41 秒，两轮模型输入都是 0。每个 worker 最终保留 1,024 个映射，累计发生 55,446–64,054 次驱逐，结果保持正确；运行中 /proc 验证每个 worker 约 3,100 个总映射、约 1,490 个文件描述符。完整两轮复测待结果更新。

13:28 已恢复完整矩阵，从 Stack 开始重跑。监控新增各进程映射数和文件描述符数，超过系统映射上限的 80% 时提前告警。另补空 epoch 的完成边界，定向测试通过；这不改变本次非空任务的采样或训练内容。


## 修复后完整两轮结果（14:29）

完整 Stack 13,228 batch / 6,772,552 样本成功完成，端到端 3665.657 秒、0.277 秒/batch，流水线 3654.427 秒。epoch 0/1 各 6,614 batch，分别 1795.610/1842.402 秒，平均损失 0.141722/0.138141。相比历史 v1（6428.7 秒 / 6614 batch），按同等 batch 数折算为 3.51×；相比 vanilla 为 4.27×，相比 batch 为 0.47×，并非每种历史实现都更快。

四个 worker 磁盘命中共 56,902,720 次，模型编码 0/6,942 条，新增写入 6,942 条；最终索引 2,891,661 条，较复测前增加 6,942 条。第二轮补充了此前缓存缺失的向量，已有向量持续从缓存复用。本次已有磁盘缓存，不能用此结果宣称首次建库无需编码。

每个 worker 的最终 mmap 数均为 1,024，累计重开约 395–397 万次，LRU 持续回收旧映射；运行中各组装进程约 3,100 个总映射，远低于 65,530 上限。四个组装进程都报告 sentinel 正常结束，无未处理异常。已越过旧挂起点并完成全部 batch；新结果追加进完整矩阵，旧中断日志保留。
