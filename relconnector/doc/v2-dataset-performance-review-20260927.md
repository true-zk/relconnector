# 十数据集性能复盘与四版本对照（2026-09-27）

## v1 与 v2 的区别

v1 是基于单进程的数据准备优化版本，通过节点去重、跨批次窗口、缓存复用和进程内线程流水线减少重复读取与编码。实际训练进一步暴露出 assemble（特征读取、编码与批次组装）的供给瓶颈：即使减少重复工作，数据准备仍可能跟不上 GPU 消费。v2 因此升级为多进程架构，将采样、assemble 和训练拆分为独立的执行阶段，分别由采样进程、组装进程池和训练主进程承担，通过有界队列连接并重叠执行。这里的单进程不等于单线程，多进程也不改变邻居采样与模型训练的算法语义。

本报告按各数据集最近一次有效完整配置成绩汇总，不按最短时间挑选。Event、F1 采用初始化优化后的两轮训练验证，Trial 采用热缓存复测，其余七项沿用最终矩阵成绩。原矩阵 46242.51 秒及原始记录保留，不覆盖历史结果。

## 四版本含义与比较口径

- Batch：全量物化特征后训练，通常更快但内存更高；例如历史 Amazon RSS 103.82 GiB。
- Vanilla：基础在线读取/特征组装版本。
- v1：历史优化在线版本，包含节点去重、跨 batch feature window、文本内存缓存等。
- v2：独立采样/组装/训练多进程流水线，共享或本地编码缓存、自适应文本缓存、持久化 embedding、初始化缓存，以及本次新增的精确数值统计分组优化。

历史三版本为 1 epoch；v2 为 2 epoch、每轮最多 10000 batch。共同配置为 batch 512、fanout 128×128、channels 128。主比较采用端到端秒/batch，包括准备工作，数值越低越好；两轮会摊薄一次性启动成本，缓存状态/机器负载/实现修订不同，因此不是严格配对性能实验。

Ratebeer 历史一轮规模为 20743 batch，v2 每轮仅取 10000，不是完整两轮遍历数据集。v1 Ratebeer 在 14400 秒时完成 15686 batch，标 * 的吞吐及比值来自超时运行估算；Vanilla 五项超时仅保留“超时”，不伪装为完整运行测量。

## 各数据集瓶颈与优化复盘

| 数据集 | 主要瓶颈/证据 | 已采用的优化 | 剩余问题与解释范围 |
| --- | --- | --- | --- |
| Amazon | 文本基数大，磁盘写入 WAL 曾增长到约 60 GB；第二轮索引读取仍慢 | 连续追加向量分片、自适应 WAL checkpoint 预算，保留 embedding 续跑 | 成绩为部分热缓存；诊断缺失，不能报编码数为 0。后加的读阶段 WAL 策略未在该完整成绩中验证 |
| Arxiv | 低文本重复率，长文本映射/编码使 GPU 等组装；最终 ready 等待 607.5 秒 | direct GloVe、并行组装、自适应持久化 embedding，跨 epoch 复用 | 矩阵开始前已有磁盘缓存；模型输入 e0/e1 为 184724/1316，仍有查询和组装成本 |
| Avito | 编码缓存查询与 SQL 较重，ready 等待 544.8 秒；模型时间很小 | 多进程流水线、编码/文本缓存复用，自适应保持磁盘文本缓存关闭 | 无独立专项修复 A/B；第二轮无文本编码仍有等待，下一步看 SQL 和共享编码缓存 |
| Event | 冷初始化主要为宽表逐列扫描、排序；数值列统计占原初始化约 80.6% | 按行数/128 MiB 预算分组读数值列、精确 partition 分位数、向量化提取；保留初始化缓存 | 空缓存初始化 2164.00→606.01 秒，减少72%；拓扑仍约270秒。主表38.77秒是热初始化训练，不能混为冷启动端到端 |
| F1 | 数据很小，启动/进程协调相对训练占比高 | 通用流水线与缓存；磁盘门槛避免不必要的持久化；新统计实现兼容 | 当前28.11秒是最新验证，旧矩阵26.57秒，不宣称本次初始化修改让F1更快；后续可测少worker |
| HM | 共享编码缓存命中却跨进程传输整块TensorFrame，RPC代价大 | 只返回请求行；HM采用4worker本地编码缓存、总预算4GiB | 流水线4603.0→1756.3秒，等待3348.9→481.9秒；本地缓存配置是矩阵显式配置，并非已自动学习最优范围 |
| Salt | 文本复用高却频繁查询共享哈希表/锁，旧共享查询约30532 worker秒 | 自适应worker本地文本→共享槽位索引，命中直接批量取向量，保留跨进程编码协调 | 完整两轮18260.2→5208.2秒；共享查询降至802.5 worker秒。剩余gather/编码缓存访问较重 |
| Stack | 共享文本表填满后探测/锁竞争；磁盘分片mmap数曾耗尽 | NumPy共享元数据、锁外哈希/gather、批量发布、mmap LRU上限1024及错误传播 | 完整3665.66秒；已有文本磁盘缓存贡献明显，仍有大量缓存读取/组装；初次无栈停滞不认定已唯一归因 |
| Trial | 共享文本缓存满，查询/磁盘发布开销高；训练端长期等数据 | 通用共享查询改进、adaptive索引及已有磁盘embedding复用 | 656.95→371.80秒，模型输入0/0；共享查询643.5→60.1 worker秒，磁盘查询544.3、SQL353.0 worker秒成为后续方向，改善包含热缓存 |
| Ratebeer | 低有效复用带来持续编码、SQL与组装开销，ready等待11389.2秒；另有共享缓存发布竞争 | 多进程与缓存复用；发布前先完成共享存储，修复并发读取损坏；保留失败输入和类别校验 | 完成2×10000；模型输入约2024.5万/2050.3万，磁盘未启用。并发修复首先保证正确性，不单独宣称是1.19×的加速原因 |

worker计时有并行及嵌套，不可相加为墙钟耗时。正确性修复、复用缓存与算子加速分开解释；未对所有数据集做逐值训练等价验收。

## 通用策略与后续优先级

1. 数值宽表：精确统计按内存预算分组；单列超预算回退流式。Event验证冷初始化提升，F1验证兼容，其他八项未用此最终版本重测。
2. 高文本复用：优先减少命中成本（本地槽位索引、批量查询），如Salt；不应因“大库”就强制启用磁盘文本缓存。
3. 高文本基数/跨轮复用：使用持久化embedding，控制WAL和mmap资源，如Arxiv/Stack/Amazon；Trial的收益也依赖此路径。
4. 编码特征复用：传输请求行而非整块；HM证明本地缓存可减少RPC，但还需一般化的运行时策略和内存权衡。
5. 后续性能优先级：Amazon/Ratebeer的SQL、文本和缓存访问；Event的拓扑构建；Avito/Trial的SQL与共享查询；F1的进程启动开销。
6. 下一次正式总评应固定最终代码、统一冷/热两组初始化与文本缓存条件，重新测十库，保留初始化/流水线/epoch分阶段计时，避免把本次混合成绩当严格公平对比。
